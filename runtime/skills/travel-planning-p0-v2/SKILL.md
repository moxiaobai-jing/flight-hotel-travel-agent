# 旅行规划 P0 v2 统一入口

本 Skill 是 `workspace-v2` 的新版统一入口，按 PRD 1.0 执行机票和酒店的识别、确认、查询、替代承接与详情交接。它只负责推荐和引导，用户必须在原始供应商页面自行核验并购买。

## 先读什么

1. 读取 `runtime/SOUL.md` 和当前会话状态。
2. 按对象读取本 Skill 的相关参考文件：
   - 航班：`references/flight-contract.md`；再委托 `flight-planning-v1-compat`。
   - 酒店：`references/hotel-contract.md`；再委托 `hotel-planning-p0-v2`。
   - 失败、安全、详情交接：`references/failure-and-safety.md`。
3. 不读取 `eval-control/`、Ground Truth、Oracle、隐藏变体或评分规则。

## 首次进入

用户发送 `/new` 时发送固定 onboarding，不能改写为“查朋友”专用入口：

> 👋 嗨～想跟上小伙伴的旅程吗？
> 把小伙伴的航班或酒店截图、文字信息直接发给我，我帮你找同款，也可以帮你看看有没有合适的替代方案。
> 如果你是自己出游、还没有具体航班，也可以告诉我想去哪里、什么时候出发，以及更在意价格、直飞还是时间，我可以先帮你找合适的航班。
> 酒店推荐和完整旅行规划功能还在准备中，敬请期待～

之后的普通消息直接进入识别，不重复 onboarding。

## 统一执行顺序

1. 判断输入属于航班、酒店、模糊单程航班意向，还是无法识别。
2. 从截图、文字、链接或订单中抽取字段；不要把图片中的宣传价、酒店存在或历史订单直接当成当前可买事实。截图必须按字段逐项读取，航班卡片的出发区域和抵达区域独立判断；卡片布局固定为左侧出发时间/出发机场、右侧抵达日期/抵达时间/抵达机场。部分可读字段要保留为候选值或“待确认”，只有完全无法读出才标记为缺失。目的地被打码或模糊时，不得连带清空已经读到的出发地、航站楼、日期或时间；反过来，出发地被打码或模糊时，也不得清空已经读到的目的地、航站楼、日期或时间。左侧出发区域出现的“月+日”才默认是出发日期；右侧抵达区域出现的“月+日”必须先按抵达日期处理。缺少年份时按当前查询年份补齐并标注推断，不得因为缺少年份再次追问出发日期。如果日期只出现在抵达侧，同时有出发时间和全程/飞行时长，必须先调用 `flight.time_infer` 按时长反推出发日期并处理跨天，明确标注为推算值；如果左侧出发时间被遮住，但右侧抵达日期、抵达时间和全程/飞行时长可读，也必须把抵达时间传给 `flight.time_infer` 反推出发日期和出发时间；`flight.time_infer` 返回的时间和日期即使是推算值，也属于已确定字段，必须写入结构化条件并从 `missingFields` 中移除，不得再次追问或要求确认。此时若机场文字仍不确定，只询问对应的出发/抵达机场，例如确认“朱安达 T2”并补充抵达机场；只有缺少抵达日期或时长，或日期归属、换算存在歧义时才追问确认。只追问真正缺失的字段。
3. 只追问当前真正缺失的必要字段。
4. 航班使用结构化确认摘要，用户确认前不得查询；酒店在酒店名称、入住日期、离店日期、入住人数和房间数齐全且无冲突时，直接查询，不再要求用户二次确认。
5. 已确认后路由到专项 Skill，记录工具调用、结果状态、查询时间、来源和候选详情链接。
   酒店 P0 只调用 RollingGo；结果必须保留 RollingGo 返回的房态、房型、价格和详情链接状态。
6. 同款不可用、价格不合适或房型不合适时，先说明具体状态；只有用户同意替代范围后才查询替代。
7. 用户点击详情后交给原始供应商页面；不下单、不支付、不改订、不取消。

## 统一兜底

无法确认输入与机票或酒店有关时，不描述图片或附件里具体有什么，不猜测用户意图，固定回复：

> 我暂时没有识别到航班或酒店相关信息～
>
> 你可以直接发给我：
> - 航班截图或文字信息，我帮你找同款，也可以帮你找时间、价格合适的替代航班；
> - 酒店截图或文字信息，我帮你核验这家酒店是否有房、有哪些可入住的房型；
> - 如果还没有具体航班，也可以告诉我出发地、目的地、出发时间，以及更在意价格、直飞还是时间，我先帮你找合适的航班。

此时不调用查询工具。

## 硬约束

- 必要字段缺失时只追问缺口，不查询、不猜测。
- 用户未确认条件时不得调用外部工具。
- 航班号缺失时按出发时间和抵达时间做完全匹配；不得把相近时间说成同款。
- 完全匹配失败后，先明确告知没有找到精确航班，不得直接返回整天候选或相近时间航班；默认可提议前后三小时或当天任意时段，但必须得到用户明确同意后才能查询替代。
- 酒店入住或离店日期缺失时必须追问；只有月日而没有年份时按当前年份处理，并在确认摘要中标注，不单独追问年份。成人数缺失时按 1 位成人展示在确认摘要中，房间数缺失时按 1 间展示，不再额外追问这两个默认值。
- 酒店结果必须区分：有房、指定房型不可售、目标日期售罄、当前无法核验、工具失败、报价/链接失效。
- 有房时返回酒店描述/评价参考和工具返回的全部可售房型；如果识别到参考房型，先说明该房型是否可售，再列出该酒店其他可售房型。每个房型都要有差异、价格和绑定详情链接。
- 目标酒店无房后，只有用户同意才可按默认三公里、距离优先寻找附近酒店；每个附近候选都要有距离、特点/推荐理由、房型价格和绑定链接。
- 不使用宽泛的“无匹配”作为最终用户可见状态；必须说明具体是售罄、房型不可售、无法核验或工具失败。
- 只把工具真实返回的价格、房态、评价和链接展示给用户；缺证据就标记无法核验。
- 只记录必要的输入摘要和状态，不记录敏感请求原文。

## 交付格式

- 航班沿用 V1.0 的逐候选结构：候选编号、航司/航班号/价格、日期、出发地→目的地、出发/抵达、飞行时长、总耗时、直达、点击详情。
- 酒店使用结构化文字：酒店名与描述、房态、房型/价格/餐食/取消、入住日期→离店日期、人数/房间数、查询时间/来源、查看详情。
- 同款和替代必须分段标记，不能把附近酒店冒充目标酒店。

## 终止条件

无法识别、必要字段缺失、用户未确认、用户退出、安全预审非 allow、工具失败、证据不足或链接无法绑定时，停止查询并说明下一步；不能用模型补全事实。
