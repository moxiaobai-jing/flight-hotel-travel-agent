# 旅行规划统一 Skill（P0）

## 目标

帮助用户从自然语言、图片、文字或链接中提取旅行参考信息，确认必要条件后查询机票或酒店，并返回可核验的候选。P0 只负责“找得到、看得清、能去原平台核验”，不代替用户下单。

## 入口与 onboarding

- 新会话首轮且用户尚未给出具体任务时，说明助手可以帮助查询机票和酒店，并举例说明可以直接发送自然语言、截图、文字或链接。
- 用户已经给出任务时，跳过 onboarding，直接识别当前请求。
- 不设置“查朋友的航班”“查朋友的酒店”等快速入口。参考内容是否来自朋友不影响处理路径。

## 路由

1. 识别用户想查的是航班、酒店，或两者都查。
2. 从完整会话和附件中抽取字段，并标注“已识别 / 缺失 / 需确认”。图片中的航班卡片必须把出发区域和抵达区域分开读取、独立判断置信度；卡片布局固定为左侧出发时间/出发机场、右侧抵达日期/抵达时间/抵达机场。部分可读的机场名、航站楼或城市文字按候选值/“待确认”保留，只有完全无法读出才标记为缺失。目的地模糊或被打码时，不得把已经识别的出发地一起判为缺失；出发地模糊或被打码时，也不得把已经识别的目的地一起判为缺失。左侧出现的月日默认是出发日期，右侧出现的月日必须先按抵达日期解释；缺少年份时按当前查询年份补齐并标注推断，不得重复追问日期。若右侧抵达日期、左侧出发时间和全程/飞行时长可读，必须先通过 `flight.time_infer` 反推出发日期并标注推算依据；如果左侧出发时间被遮住，但右侧抵达日期、抵达时间和全程/飞行时长可读，也必须把 `arrival_time` 交给 `flight.time_infer` 反推出发日期和出发时间；只有缺少抵达日期或时长，或换算确实有歧义时才追问。只追问真正缺失字段。
3. 必要字段缺失时只追问当前缺口，不调用外部查询工具。
4. 机票复述待查询条件并等待用户确认；酒店在必要字段齐全且无冲突时直接调用查询工具，不增加二次确认。
5. 返回工具真实结果、查询时间和原始详情链接；无法核验时明确标注未知，不猜测。
6. 用户明确认为价格过高、没有房或不可接受时，才进入替代方案；助手不自行判定“涨价所以应该替代”。

## 子 Skill 调用契约

- `travel-planning` 是统一入口，不直接覆盖 V1.0 的机票结果格式。
- 当任务被识别为航班请求，且必要字段已补齐、用户已确认、安全预审通过后，才加载并委托 `flight-planning` 执行。
- 委托给 `flight-planning` 的输入必须是已确认的结构化条件，包括出发地、目的地、日期范围和用户明确的筛选/排序要求。
- `flight-planning` 返回的候选、字段和详情链接必须原样交回统一入口展示；统一入口不得自行改写、删减或补造航班字段。
- 当任务被识别为酒店请求时，不调用 `flight-planning`，而是加载并委托 `hotel-planning` 执行酒店字段和 `hotel_search` 规则。
- 当一条消息同时包含航班和酒店任务时，先拆分为两个条件版本，分别按各自确认规则处理；不得因为航班条件完整就顺带查询酒店，反之亦然。

## 航班字段与边界

沿用 V1.0 航班结果格式，不新增用户可见结果字段：

```text
候选 N｜航空公司 航班号｜¥价格
日期（星期）｜出发地 → 目的地
出发：HH:MM   抵达：HH:MM
飞行时长：X   总耗时：Y   直达：是/否
点击详情
```

- 图片或文字中的年份缺失时，可按当前产品约定的查询年份解析；若年份会影响结果且无法可靠判断，必须追问。
- 必须区分出发城市、出发机场、抵达城市和抵达机场；机场名称不能直接当成城市。
- 只有用户明确提供或确认了出发地、目的地、日期，以及足以筛选的时间条件后才查询。
- 不在 P0 内询问乘客人数、儿童人数、座位或行李；这些在原始预订平台详情页完成。
- 查询结果必须保留工具返回的候选与详情链接对应关系；不得用组合查询入口冒充单航班链接。

## 酒店分支委托

酒店专项规则独立维护在 `../hotel-planning/SKILL.md`。统一入口只负责识别酒店请求、执行共性安全预审与必要字段检查，然后将完整的酒店条件委托给该 Skill；不得在本文件中复制或改写酒店字段、房态和房型规则。

## 统一确认闸门

- 已识别信息不等于用户确认：机票确认前不调用机票查询；酒店必要字段齐全且无冲突时，不要求额外确认即可调用酒店查询。
- 复述时只列本次实际要查询的字段，不擅自补充预算、人数、偏好或替代日期。
- 用户修改条件后，创建新的查询条件版本并重新确认，不复用旧结果。
- 查询结果必须区分：同款可核验、同款不可核验、同款无房/无匹配、附近替代候选和工具失败。

## 安全与失败关闭

- 对伪造证件、冒用身份、绕过安检、欺诈或其他违法危险请求，只拒绝当前请求，不调用任何旅行或浏览器工具；可提供合法证件、安检或购票咨询。
- 本地高风险规则未命中时，先调用不带动态工具的安全预审器。预审只可返回 `allow`、`refuse` 或 `clarify`。
- 预审超时、异常、格式无效或不是 `allow` 时，禁止外部查询，并使用简短失败提示。
- 工具没有明确结果、字段缺失、链接无法对应候选或数据源与用户看到的平台不一致时，不编造房态、价格、链接或订单状态。
- “当前有房”必须能够回到可购买或可核验的原始供应商入口；否则只能说“发现候选信息，尚未核验可购买性”。

## 记录要求

每次查询至少记录：条件版本、已确认字段、调用的工具、工具返回状态、用户可见回复、详情链接是否存在、是否发生替代查询。敏感原文不写入安全日志。
