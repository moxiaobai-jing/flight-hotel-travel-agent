# J-05：异常分类与重试

## 测试目的

验证机票规划助手能区分四类异常，并按照异常原因决定是否重试、重试哪些组合以及何时停止自动重试：

1. 查询超时；
2. 数据源限流；
3. 查询成功但没有匹配结果；
4. 普通失败，并且已经达到 3 次重试上限。

本路径使用 `eval/fixtures/J-05-controlled-results.json` 中的受控结果。受控结果只验证状态处理和用户文案，不代表真实航班事实。

## 四类异常的判定

| 异常类型 | 一般触发条件 | 与其他异常的区别 | 是否自动重试 | 用户可见说明 |
|---|---|---|---|---|
| 超时 | 单个组合在工具或上游请求的截止时间内没有完成，出现请求超时、读取超时或上下文取消 | 没有拿到该组合的完整结果；不等于“没有航班” | 是，只重试未完成组合，且不能扩大原查询范围 | “这部分查询超时，暂未完成，可以重试未完成的组合。” |
| 限流 | 上游返回 HTTP 429、`rate limit`、`too many requests` 或明确的配额/频率限制 | 这是上游拒绝当前请求，不代表该日期没有航班 | 是，按退避间隔重试；不能通过瞬间增加并发继续请求 | “这部分查询受到限流，可以稍后重试。” |
| 无匹配 | 请求成功、响应结构有效，但筛选条件下返回空候选 | 工具调用成功，只是结果集合为空；不能把它当成工具失败 | 否；重试不会改变事实结果，应建议修改条件后重新搜索 | “没有找到符合条件的方案，可以修改条件后重新搜索。” |
| 普通失败且达到上限 | 非超时、非限流、非无匹配的错误，例如上游 5xx、响应格式错误、网络错误或业务失败；同一组合已经重试 3 次 | 这是可重试失败，但继续重试已超过策略上限 | 否；标记为失败并等待用户修改条件或明确重新搜索 | “这部分查询失败，已达到重试上限。可以修改条件后重新搜索。” |

### 重试计数口径

“达到 3 次上限”指同一组合已经完成 3 次自动重试，即首次请求之外最多再尝试 3 次。`retryCount >= 3` 时不得继续自动重试。

## 人工走查步骤

1. 运行受控 Demo：

   ```bash
   node tools/run-controlled-j05.mjs
   ```

2. 确认输出至少包含以下状态：`timeout`、`rate-limited`、`no-match` 和 `failed`。
3. 确认允许重试的组合只包含未完成且仍未达到上限的超时、限流和普通失败组合。
4. 确认 `no-match` 和 `failed + retryCount=3` 不在重试列表中。
5. 确认重试范围只使用原始查询中的组合，不新增目的地、出发地或日期。

## 真实对话走查说明

自然语言本身通常不能稳定制造真实的超时或限流。真实环境中的这些异常应由工具层记录上游返回和耗时后分类；评测时使用受控 fixture 或测试开关复现，不能让模型凭空声称发生了超时、限流或无匹配。

若真实查询出现异常，助手应先说明准确原因，再给出下一步：

- 超时：保留已完成结果，说明哪些组合尚未完成，并只重试未完成组合；
- 限流：说明请求过于频繁或达到上游限制，等待退避后再重试；
- 无匹配：说明查询已成功但没有符合条件的航班，建议用户修改条件；
- 普通失败达到上限：停止自动重试，说明已达到上限，等待用户修改条件或明确发起新一轮查询。

## 通过标准

- 四类异常的状态和用户说明不混淆；
- 无匹配不被误报为系统故障；
- 达到 3 次重试上限后不再循环重试；
- 重试不扩大原始搜索范围；
- 已完成组合的结果不会因为其他组合异常而被丢弃；
- 受控 Demo 明确标记为 Demo 数据。
